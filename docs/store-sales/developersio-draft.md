# 時系列基盤モデルを小売需要予測に入れてみた — うまくいったこと、いかなかったこと

> DevelopersIO記事草稿。スコアと体験は `src/lib/competitions/store-sales-experiments.ts` と同期する。

## はじめに

Kaggleの「Store Sales - Time Series Forecasting」に、Amazon Chronos-2、Google TimesFM 2.5、LightGBMを持ち込みました。結果は公開LB **0.39515**。上位帯の0.37にはまだ届きませんが、「基盤モデルなら混ぜれば強い」「履歴は長いほどよい」「ゼロが続けば0にすべき」という、もっともらしい考えが実際には外れる過程を記録します。

この記事で伝えたいのは最終スコアだけではありません。何を試し、どこで悪化し、数字からどう考え直したかです。

## まず、何を予測するのか

エクアドルのスーパーマーケット54店舗、33商品ファミリー、合計1,782系列について、2017年8月16日から31日までの16日間を予測します。提出は28,512行。評価指標はRMSLEです。

末尾16日を完全に隠すローカル検証を作りました。未来16日を一括で当てるモデルでは、売上ラグを16日以上に限定します。ここを守らないと、検証時にしか知り得ない直近売上を使うことになります。

## 最初の結果

| 試行 | ローカルRMSLE | 採否 |
| --- | ---: | --- |
| 同じ曜日の直近 | 0.61704 | 不採用（下限として保存） |
| 一括LightGBM | 0.43653 | 不採用 |
| TimesFM 2.5 | 0.46438 | 不採用 |
| Chronos-2（長い文脈） | 0.4136 | 不採用 |
| Chronos-2（直近540日） | 0.40476 | 採用 |
| 逆RMSLEで単純混合 | 0.42822 | 不採用 |
| ゼロ系列を21日ルールで補正 | 0.41187 | 不採用 |
| Chronos-2 74% + LightGBM 26% | 0.40002 | 旧Champion |
| 再帰LightGBM 58% + Chronos-2 37% + 一括LightGBM 5% | **0.39020** | 新Champion |

公開LBは **0.39515** でした。ローカルとの差が0.005なので、以後の改善判断にこの検証を使えると考えています。

## うまくいった: Chronos-2に未来共変量を渡す

Chronos-2には直近540日の売上と、未来にも分かるプロモーション、祝日、原油価格、給料日を渡しました。0.40476で単体一位です。売上系列だけを渡したTimesFMは0.46438だったため、このコンペでは外生変数の有無が大きいと考えています。

断定はできません。モデル構造の差もあります。ただ「基盤モデル」という括りより、「この問題で未来に分かる情報をどう渡せるか」が重要でした。

## うまくいかなかった: 履歴を長くすれば強い

Chronos-2に長い履歴をそのまま渡したときは0.4136でした。直近540日に絞ると0.4048へ改善し、実行時間も約17分から約6分半へ短縮しました。

仮説は、2013年の古い需要構造や2016年の地震など、現在と違う局面が直近のパターンを薄めたことです。長いコンテキストを持つモデルでも、長く入れること自体が目的になってはいけませんでした。

## うまくいかなかった: 基盤モデルを全部混ぜる

各モデルの逆RMSLEを重みにした混合は0.42822。Chronos-2単体より大きく悪化しました。逆数ルールでは弱いモデルにも必ず重みが付くためです。

そこで、RMSLEと同じlog空間で非負最小二乗を解きました。重みはChronos-2 74%、LightGBM 26%、TimesFM 0%。「基盤モデルを入れた」という理由ではなく、検証で効いたものだけを残しました。

## うまくいかなかった: ゼロが21日続けば取扱終了

直近21日の売上が0なら予測を0にする後処理は、0.4048から0.4119へ悪化しました。一時的に売れていない系列を取扱終了と誤認したと考えています。

0・3・7・14・21日を検証で選ぶようにすると、今回は「後処理なし」が勝ちました。競合解法で効いたルールでも、自分の予測と検証窓で再確認が必要です。

## 次に試している: 1日ずつ進める再帰LightGBM

一括LightGBMは、未来漏洩を防ぐためラグ16日以上しか使えません。ところがデータには7日周期が強くあります。そこで商品ファミリー別にモデルを作り、1日目の予測を履歴へ戻し、2日目でlag_1として使う再帰予測を実装しました。これなら1・7・14日前を安全に使えます。

結果は再帰モデル単体 **0.3966**、Chronos-2 37%・再帰LightGBM 58%・一括LightGBM 5%の混合で **0.3902** でした。旧Championの0.4000から0.0098の改善です。公開解法で報告されていた「近い週次ラグが効く」を、自分の検証でも再現できました。

次に木の本数と学習期間を一つずつ変えました。木を140本に減らすと0.39884、320本へ増やすと **0.39584**。学習期間を730日から365日へ縮めると0.40232、1095日へ伸ばすと0.40030でした。したがって、木は320本、期間は730日を次の候補にしました。古いデータを増やすだけでは改善しない点はChronos-2と同じでした。

さらに、再帰誤差を避ける対照として「予測距離別LightGBM」を追加しました。予測日の1〜16日先という距離に応じて、その時点で既知の直近値と週次ラグだけを選び、16日を一括予測します。未来の実績を別の値に置き換えても出力が変わらないテストで、漏洩がないことを固定しています。

結果が悪くても削除しません。Run ID、ローカルスコア、公開LB、採否、原因仮説を不変の成果物として残します。

## 実験を上書きしない仕組み

各実験は `outputs/store-sales/runs/<run-id>/` に保存します。一度作ったRunは変更しません。人が読む名前はタグとして別管理します。

- `champion`: 現在採用しているRun
- `previous-champion`: 直前のChampion
- `baseline`: 公開LB 0.39515の最初の提出
- `latest`: 最後に走らせたRun（悪くても残る）

ローカルRMSLEが悪いRunはChampionになりませんが、履歴と知見には残ります。任意のRunへ戻すと、result.jsonとsubmission.csvがその時点のものへ復元されます。

## まとめ

- Chronos-2の未来共変量は効いた
- 履歴は長ければよいわけではなかった
- TimesFMは今回の単変量利用では効かなかった
- 弱いモデルを機械的に混ぜると悪化した
- 他解法のゼロ補正も、そのままでは悪化した
- ローカル検証と公開LBの差は0.005で、改善判断の土台は作れた

1位は保証できません。ただし、悪化した試行も含めて再現可能に残し、数字が改善した変更だけをChampionへ進めます。続きは再帰LightGBMの結果とともに追記します。
